# Pre/Post Implementation Measurement — 2026-09-12

This report compares the pre-implementation `main` snapshot with the completed implementation stack on the same GitHub Actions runner.

- **Before:** `d44adbbe224e38aacf2caad43c32dc482fc23bf8`
- **After:** `dec889c9df42009930da9c6cadd6bbfe525caea2`
- Common test scene, common Node/GitHub Actions environment
- Tool latencies were measured three times inside each run; the table below uses the median.
- The comparison workflow itself was re-run four times to expose CI timing variance.

## 1. MCP surface / context cost

| Metric | Before | After | Change |

## 3. Runtime latency

Four independent comparison jobs were run. Each job measured each tool three times and reported the per-job median.

| Run | create before → after | render before → after | lint before → after | critique before → after |
|---|---:|---:|---:|---:|
| 1 | 12.5 → 18.0 ms | 10.0 → 9.7 ms | 2.9 → 1.2 ms | 31.2 → 32.2 ms |
| 2 | 14.4 → 25.0 ms | 10.1 → 12.4 ms | 1.4 → 1.7 ms | 38.2 → 26.7 ms |
| 3 | 16.1 → 23.1 ms | 8.8 → 12.6 ms | 1.5 → 1.8 ms | 34.3 → 26.4 ms |
| 4 | 12.4 → 28.6 ms | 8.1 → 13.7 ms | 1.8 → 2.2 ms | 31.7 → 37.4 ms |

### Interpretation

- **`riv_create` is consistently slower** after the change. The added cost ranged from about **+5.5 ms to +16.2 ms** in these runs. This is the expected cost of hashing, immutable metadata creation and revision-object persistence.
- The median of the four per-run create medians is roughly **13.5 ms before vs 24.1 ms after**. Treat the percentage as indicative, not a stable microbenchmark.
- Render/lint/critique results vary enough between runners that no strong performance conclusion should be drawn. There is no consistent large regression signal outside create.
- The absolute create overhead is still in the tens of milliseconds, while it buys deterministic revision identity and delivery gating.

## 6. Implementation cost

Git comparison from before → after:

- **78 commits**
- **31 files changed**
- **1,969 additions**
- **175 deletions**
- **2,144 changed lines**
- npm test scripts: **4 → 13**
- compiled `dist/` size: **944,851 → 967,457 bytes (+2.4%)**

This is a meaningful increase in implementation and maintenance surface. The trade is favorable only if immutable review/delivery, provenance and repeatable release verification are actual product requirements; they are not “free architecture.”

## 7. Bottom line

The measurable result is:

1. **Common rendering behavior stayed byte-for-byte identical** for the controlled scene.
2. **MCP prose context got materially smaller** despite adding a tool and richer functionality.
3. **Schema and compiled-code size increased modestly**.
4. **Create latency increased consistently by low tens of milliseconds**, directly attributable to revision persistence.
5. **Safety and auditability changed qualitatively**: stale reviews are rejected, final output is tied to reviewed bytes, provenance survives edits, and the entire flow is exercised from an empty workspace.
6. **Test surface more than tripled** (4 → 13 scripts), which raises maintenance cost but substantially reduces unverified release behavior.

The main remaining performance question is whether revision-store I/O becomes material under high-throughput batch authoring. The current measurements show a clear per-create overhead but do not test hundreds/thousands of revisions or a slow/network filesystem.
