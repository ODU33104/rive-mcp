Date: 2026-09-12

## Mission

Run the creative-quality A/B that could not be executed in ChatGPT without API credentials.

The purpose is to answer one question with evidence:

> Given the same natural-language brief, does the post-architecture rive-mcp workflow help an AI agent produce better final Rive work than the pre-change version?

Do **not** implement new rive-mcp product features during this test. If the benchmark harness itself is defective, fix only the harness and document the fix.

## Test design

Nine common briefs are fixed in `test/ab/briefs.json`.

Pilot briefs:

- `fintech-status-card`
- `weather-micro-interaction`
- `existing-file-refinement`

Run the pilot first:

- same Claude model/configuration for A and B;
- one fresh session/workspace per version/brief;
- no cross-run memory;
- no human correction during generation;
- same brief text verbatim;
- same time/turn budget;
- baseline gets its baseline bundled design guidance;
- current gets its author/refine + QA + design-guidelines workflow;
- save final `.riv`, standardized preview and critique/filmstrip.

If pilot mechanics are valid, run the full benchmark:

- 9 briefs × 2 versions × 3 independent repeats = **54 runs**.

If 54 runs are operationally excessive, do **not** silently reduce the experiment. Run 18 runs (one repeat) as an explicitly labeled preliminary result, then decide whether to continue.

## Claude Code execution strategy

Because this is being run inside Claude Code rather than through the OpenAI API harness, use Claude Code itself as the authoring agent.

For every run:

1. create a clean temporary workspace;
2. checkout/build exactly one fixed rive-mcp ref;
3. expose/connect that checkout's MCP server to the run;
4. provide only the fixed brief plus that version's intended workflow guidance;
5. allow the agent to use rive-mcp normally;
6. require a real final `.riv`;
7. run lint and critique;
8. save the final artifact and visual evidence;
9. record the run metadata before starting the next run.

Do not let the current checkout's skills leak into baseline runs.

## Token measurement

The original API harness records exact API usage fields. Claude Code may expose different usage accounting.

Record exact token/cache/context figures **only if Claude Code exposes them directly and consistently for every A/B run**.

If exact comparable telemetry is unavailable:

- mark `tokenMeasurement = unavailable`;
- preserve the already-measured MCP character/context proxy separately;
- do **not** estimate tokens from characters;
- do **not** publish a “token reduction %” claim.

Useful non-token efficiency metrics that remain valid:

- tool calls;
- create/edit calls;
- lint/critique cycles;
- retries/tool errors;
- wall-clock time;
- completion rate.

## Blind evaluation

Do not score while knowing A/B identity.

Use the seven 1–5 dimensions in `test/ab/rubric.json`:

1. brief adherence;
2. composition/hierarchy;
3. visual polish;
4. motion/easing;
5. readability;
6. coherence/restraint;
7. technical correctness.

Also record:

- obvious broken artifact: yes/no;
- ship without manual visual correction: yes/no.

Randomize outputs into opaque sample IDs. Keep the A/B mapping hidden until all scores are committed.

Prefer two independent evaluators. If only one evaluator is available, state that limitation prominently.

## Analysis rules

Report baseline and current separately for:

- mean/median blind quality;
- every quality dimension;
- completion rate;
- ship-without-correction rate;
- broken-artifact rate;
- per-brief result;
- tool calls;
- wall-clock time;
- retries/errors;
- exact token usage only when truly available.

A global mean is insufficient. A workflow can improve authoring while regressing refinement or state-machine tasks.

Do not convert a 1–5 quality-score difference into a percentage improvement without explaining the calculation. Prefer “3.4/5 → 4.0/5.”

## Promotion threshold

Treat “creative quality improved” as supported only if:

- no meaningful completion-rate regression;
- current wins mean blind quality on at least 6 of 9 common briefs;
- no critical technical-correctness regression;
- failures/regressions are disclosed.

If the result is mixed, say it is mixed. Do not optimize the benchmark after seeing outcomes.

## Public-story evidence

The investigation that led to this architecture studied:

- https://github.com/matthew-kissinger/kiln
- https://kilnstudio.tools/

The defensible framing is that Kiln was studied as a reference for AI-assisted creative workflow thinking, and rive-mcp adapted broader ideas around workflow separation, iterative visual review and explicit human/agent handoff.

Do not claim Kiln code was copied or that Kiln implements rive-mcp's exact revision/review/finalize architecture unless independently verified.

## Stop conditions

Stop and document rather than improvise if:

- a fixed ref no longer builds;
- baseline/current cannot be isolated fairly;
- the same model/config cannot be used for both;
- blind identity is accidentally revealed before scoring;
- a brief requires changing after one version has already run;
- token telemetry differs in semantics between A and B.

The integrity of the comparison matters more than obtaining a favorable result.

## Return condition

The handoff is complete when the pilot has been executed and inspected for methodological defects. The full 54-run benchmark should then be executed unchanged if the pilot is sound.

When finished, return the evidence directory and a short summary of:

- what improved;
- what regressed;
- whether creative-quality improvement is actually supported;
- whether an exact token claim is supported;
- any benchmark limitations.
