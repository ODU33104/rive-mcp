## 0. 依頼者の本当の目的

`rive-mcp` のゴールは検証ツール数の増加や「レシピ辞典」自体ではなく、**ユーザーが一度自然言語で依頼するだけで、予想以上に完成度の高い、編集可能なRive作品を得る**こと。

ユーザーの重要な着想：
- 時計は、文字盤の円・外周飾り・短針・長針・秒針・中心回転軸・影・反射・背景・文字等の部品と、それぞれの動き、関係性から成る。
- 完成作品を再利用不能な塊として保存せず、**部品・装飾・モーション・配置・時間順序・親子関係・意図**に分解する。
- AIが指示に応じて部品や動きを選んで組み立て、元の題材以外（例：腕時計→イヤホン→計器UI）へ展開する。
- レシピ数と分解知識は並列に増やす。使える公開情報は積極的に参照するが著作権・ライセンスは遵守する。

今回提案された暫定5層：
1. Intent（ユーザーの目的・テイスト・否定条件・制約）
2. Scene Blueprint（レイアウト／画面構成）
3. Part Atlas（部品／取付点／支点／親子関係／装飾）
4. Motion Primitive Atlas（独立した動き／キーフレーム／タイミング／適用対象）
5. Assembly Grammar（相性、階層、制約、順序、組み合わせ、因果的な演出意図）
加えて、実行主体として Scene Constructor（Prompt → intent → blueprint → parts → motions → Rive）。

**これは仮説。名称・層数・境界・データモデルを所与の正解として扱わない。** あなたにはこれが最善かを疑ってもらう。

## 2. 必ず反証する論点（結論を先取りしない）

### A. なぜこの方式で「見た目の品質」が上がるのか？

完成品を部品に分けると再利用性が増すのは自明に近いが、**美的完成度が増すとは限らない**。
- 解体で失われる構図、一貫性、視線誘導、配色、アートディレクション、テクスチャ、独自性は何か？
- 局所的に正しい部品を大量に集めると、全体が凡庸・雑然としないか？
- 完成例検索＋画像理解＋類似シーン編集、手続き的テンプレート、LLMの都度コード生成、scene graph＋制約ソルバー、プログラム合成、階層文法などを**同じ評価条件**で比較。
- 自動分解を無理に広く行うより、少数の優れた完成シーンから派生させた方が強い可能性を検討。

### B. 正しい分解単位・表現は何か？

- Part は SVG path / Rive shape / group / bone / nested artboard / character rig / semantic assembly のどの粒度か？
- 時計針の pivot は親の中心、ローカル原点、回転変換に依存。親子の座標系、スケール・回転合成、角度単位、寸法正規化、z-order、マスク、クリッピング、グラデーション、フォント・文字送り、3D風の奥行き等を再利用可能に表現できるか？
- 部品間に役割・制約があること（秒針は中心回転、影は本体と同期、光沢はマスクされる）を、単なる「互換タグ」ではなく **attach points / pivots / parameter constraints / temporal relations / capabilities** で示せるか？
- 共通プリミティブにしすぎると、作品固有の豊かな演出情報が失われるのではないか？
- 静的構造（見た目）と動的構造（state machine、pointer/data inputs、loops、transitions）を同じモデルへ無理に詰め込んでいないか？

### C. 分解できることと再合成できることは別

SOLSTICEを**実際に**3階層以上に分解した例を構築、またはソース行に基づき具体化する：
- Scene → semantic assemblies（dial/watch/copy/fx）→ parts（case, ring, hands, glint, shadow）→ primitive shapes/motions
- 部品の親子、支点、データ依存、時間依存と必要な外部仕様の明記。
- 少なくとも3種類の部品について、**別の題材に置換する場合どの情報が不足するか**を示す。
- 安易な「時計→イヤホンへ自動転用可能」を否定する具体的な反例を用意。意味が異なる題材に元の針回転演出を適用するのは適切か？
- 分解→再合成で同一シーンが壊れず復元できるか、保存に必要なroundtrip情報を特定。

### D. レシピを際限なく増やす戦略の是非

- 60→150→300→1000件への量的拡張で、重複、誤検索、ロングテール低品質、著作権、執筆コスト、ライセンス検証コストはどう増える？
- **タグや名前だけの部品が増える虚構の成長**を見破る評価指標を出す。
- dedup・clustering・provenance・maturity gates・検索段階化・再利用可能部品の品質点数をどの層に置くべきか。
- Lottie、CSS、GSAP、React、Rive間の抽出・変換の損失（SVGのpath、マスク、レイアウト、スクリプト、インタラクション等）を具体的に検討。

### E. 自然言語→計画→実行の信頼性

- 例：「工業的で静かな腕時計。秒針だけ生きている」「静かな成功演出、弾ませない」「イヤホンの高級な発売演出」。否定や程度、タイミング、題材、装飾の矛盾をどう扱う？
- LLMに構造化プランを出させるだけで済むのか、制約解決・asset resolver・style token system・semantic search・fallback templatesが必要か？
- 明示的に実装可能なもの、生成AIのセンスに依存するもの、未解決事項を切り分ける。
- 「一発生成」はユーザー入力が一度という意味。内部の複数候補生成・プレビュー・選択／改良は許されるが、現実の計算コストと体感時間を考慮する。

### F. 技術・プロダクト・権利の安全性

- 公式Rive CLI/RML/MCPを実行backendとして使う前提と、rive-mcp独自の価値の境界。
- 公開例の参照、ライセンス上認められた改変、コードの再配布、メディアの大量自動収集を厳密に分ける。
- 出典不明の作品を「元作者が公開しているから使ってよい」とみなさない。
- 対象ユーザー・価値の仮説、作品の美的な主観評価と工学的実行確認の違い。

## 3. 必須の比較実験案

「このアーキテクチャが必要」という感想で終わらせない。**反証可能な低コスト実験を最低3つ**提案。

実験例：
1. 同一プロンプト／同一画像・フォント／同一モデルで、(A)現行60レシピ、(B)完成人気シーンの改変、(C)分解されたPart+Motion Grammarの再合成を比較。**初回出力の美的評価（ブラインド）**、テーマ適合、編集可能性、生成時間、コストを測定。
2. SOLSTICEを分解→元の姿へ再構成し、同一設定の公式ランタイムでフレーム差分・部品階層・動作を検証。元の見た目を再現できなければ一般化は難しい。
3. 「時計→イヤホン」「時計→抽象計器」「成功演出→通知UI」へ転用。完成シーンの改変とPart/Grammarで**一般化の質**が改善するか検証。
4. 60→120などの拡張時に従来106問に加えて**未知のHoldoutと新規レシピ専用意図**でTop-k、禁則違反、abstain、誤適用を測る。

各実験の最小サンプル、ベースライン、見逃せない失敗条件、続行/中止判断を提示すること。雰囲気だけの主張は不可。

## 4. 提出物（このレビューが成功とみなされる条件）

**日本語**で、以下の見出しを持つ独立批評を作る。論点ごとに「確認済事実 / 推論 / 未検証仮説」を区別し、可能な限り **GitHubパス・該当行・CI/参考URL** を挙げる。

1. **総合判定**: `GO` / `CONDITIONAL GO` / `NO-GO`。最初に結論と理由。容赦なく。
2. **致命的な欠陥 Top 5**: 構想が成立しない条件を優先順位順に。
3. **前提の誤り・証拠不足**: 「分解可能＝再合成可能＝高品質」等を批判。
4. **代替アーキテクチャ比較**: 少なくとも3案。選択/棄却理由とコスト。
5. **修正版の具体アーキテクチャ**: 採用するとしたら最小のschema概念・実際のRive対応表・データの責務・契約。タグを並べるだけでは不可。
6. **SOLSTICEの具体的分解と再合成の問題点**: どの既存コードで可能で、何が未実装か。
7. **拡大の中止基準**: レシピ追加が逆効果になる定量条件とライセンスゲート。
8. **2週間以内で結論が出るMVP実験計画**: 3件以上の比較実験、成果物、判定基準。
9. **優先順位**: `Build now` / `Defer` / `Reject`。時間・開発コストをざっくり見積もるなら根拠も記す。
10. **独立審査の最終提言**: 私たちの案に迎合しない、明快な是非。
